# ARC-001: System Architecture - Orchestrator Pattern

## Context

The Ollama-MCP Filesystem Orchestrator needs to bridge local LLM models (Ollama) with filesystem operations via the Model Context Protocol (MCP). The system must provide an autonomous agent loop that can plan multi-step tasks, execute filesystem tools safely, and reflect on progress.

## Problem Statement

**How do we enable local LLMs to safely interact with the filesystem through a structured agent loop?**

### Challenges

1. **Safety**: LLMs can generate arbitrary paths → need security sandbox
2. **Autonomy**: Need agent loop that plans, executes, and reflects without constant user input
3. **Reliability**: Tool failures must not crash the agent loop
4. **Performance**: Tool execution must be fast (< 100ms p95)
5. **Observability**: Users need visibility into what the agent is doing

## Architectural Style

**Monolithic Python Application** with modular internal architecture.

### Rationale

| Option | Pros | Cons | Decision |
|--------|------|------|----------|
| **Microservices** | Scalable, independent deployment | Overkill for single-user tool, network overhead | ❌ Rejected |
| **Monolith** | Simple, fast, easy to debug | Limited scalability | ✅ **Selected** |
| **Plugin Architecture** | Extensible | Complex for v0.1.0 | ⏸️ Future consideration |

### Trade-offs

**Chosen**: Monolith
- ✅ Single `uv tool install` deployment
- ✅ No network latency between components
- ✅ Simpler debugging (single process)
- ❌ Future scaling requires refactor (acceptable for local tool)

## Component Boundaries

```
┌─────────────────────────────────────────┐
│           CLI Layer                      │
│  - Typer commands                       │
│  - Rich formatting                      │
│  - User interaction                     │
└─────────────────────────────────────────┘
              ▼
┌─────────────────────────────────────────┐
│        Orchestrator Core                │
│  - Agent loop (ReAct)                   │
│  - Tool registry                        │
│  - Conversation management              │
└─────────────────────────────────────────┘
         ▼                  ▼
┌──────────────────┐  ┌──────────────────┐
│  Ollama Client   │  │   MCP Server     │
│  - LLM calls     │  │  - 9 FS tools    │
│  - Retry logic   │  │  - Security      │
└──────────────────┘  └──────────────────┘
```

### Rationale

**Layer Separation**:
- **CLI**: Handles user interaction, delegates to orchestrator
- **Orchestrator**: Business logic, agent loop, no UI concerns
- **Ollama Client**: Isolated LLM communication, testable with mocks
- **MCP Server**: Filesystem operations, security enforcement

## Data Flow

### Happy Path: 3-Step Query

```
1. USER → "List Python files in ~/projects, read the largest, summarize imports"

2. CLI → Parse command → Initialize Orchestrator

3. ORCHESTRATOR ITERATION 1:
   - LLM plans: "Need to search for *.py files"
   - Tool call: fs_search(pattern="*.py", path="~/projects")
   - Tool result: Found 8 files
   - Add to context

4. ORCHESTRATOR ITERATION 2:
   - LLM plans: "Need file sizes to find largest"
   - Tool call: fs_file_info for each file
   - Tool result: main.py is largest (4.5 KB)
   - Add to context

5. ORCHESTRATOR ITERATION 3:
   - LLM plans: "Read main.py content"
   - Tool call: fs_read_file(path="~/projects/myapp/main.py")
   - Tool result: <file content>
   - Add to context

6. ORCHESTRATOR FINAL:
   - LLM reflects: "I have all info, can answer now"
   - Response: "Found 8 Python files. Largest is main.py (4.5 KB). Imports: fastapi, pydantic, ollama"

7. CLI → Format and display response to user
```

## Security Architecture

### Defense in Depth

```
Layer 1: Path Validation
   ↓ Resolve paths, check for ../
Layer 2: Sandbox Enforcement
   ↓ Verify within ALLOWED_PATHS
Layer 3: Permission Checks
   ↓ os.access() for read/write
Layer 4: Confirmation Prompts
   ↓ User approval for destructive ops
Layer 5: Audit Logging
   ↓ JSONL trail of all operations
```

### Rationale

**Why 5 layers?**
- Single layer can fail (e.g., path validation bypass)
- Multiple layers provide redundancy
- Audit trail enables forensic analysis

## Scalability Considerations

### Current (v0.1.0)

- **Users**: 1 (single-user local tool)
- **Concurrency**: 1 (sequential tool execution)
- **Storage**: Local filesystem only

### Future (v0.2.0+)

- **Multi-conversation**: Parallel sessions for power users
- **Remote MCP**: Network filesystem access
- **Distributed Ollama**: Load balancing across multiple instances

**Decision**: Don't optimize for scale in v0.1.0 - premature optimization.

## Consequences

### Positive

- ✅ Simple deployment (single command: `uv tool install`)
- ✅ Fast tool execution (< 100ms p95)
- ✅ Easy debugging (single process, comprehensive logging)
- ✅ Secure by default (5-layer security)

### Negative

- ❌ No horizontal scaling (single process)
- ❌ Memory bound by conversation history
- ❌ Ollama must be local (no remote LLM support in v0.1.0)

### Mitigations

- **Scaling**: Not needed for single-user tool
- **Memory**: Context truncation at 32K tokens
- **Remote LLM**: Future feature (v0.2.0)

## Open Questions

1. ❓ Should we support streaming responses from Ollama? (v0.2.0 consideration)
2. ❓ Should we cache tool results? (LRU cache for idempotent reads)
3. ❓ Should we support multiple simultaneous conversations? (v0.2.0 feature)
